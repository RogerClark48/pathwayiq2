WHAT THE APP DOES
-----------------
FutureFinder is a career guidance tool for the Greater Manchester Institute of
Technology (GMIoT). It helps prospective students — school leavers, adult
returners, career changers — find courses and understand the careers they lead to.

The app starts with a conversational welcome interview conducted by an LLM
(Claude Sonnet). Once the user has given enough signal about their interests,
the interview pivots to showing matching courses. Users can then browse courses,
view connected career paths, and continue asking questions through a chat interface.

Data served: 83 GMIoT courses (across 6 partner providers) + 1,252 NCS/Prospects
job role records, connected by pre-computed semantic similarity scores.


HOW TO RUN IT
-------------
1. Ensure .env exists in the project root with:
     ANTHROPIC_API_KEY=...
     VOYAGE_API_KEY=...
     (SKILLS_ENGLAND_API_KEY is pipeline-only — not needed to run the server)

2. Start the server:
     C:\Dev\pathwayiq2\venv\Scripts\python.exe api.py

3. Open http://localhost:5000 in a browser.
   Always open via the server, not directly from the filesystem — Flask serves
   the frontend statically and direct file:// access breaks API calls.

Optional environment variables (all have defaults safe for local dev):
  SECRET_KEY        Flask session signing key (default: "dev-fallback-key" — change in prod)
  ADMIN_PASSWORD    HTTP Basic Auth password for /admin/* routes (default: "admin")
  AUTH_ENABLED      Set to "true" to gate the app behind access codes (default: false)
  SEED_ACCESS_CODE  If set, this access code is auto-created permanently on startup
  PORT              Port to listen on (default: 5000 in dev, 8000 in prod via gunicorn)

DATABASES IN DETAIL
-------------------

futurefinder.sqlite
  Tables: courses, providers, campuses, course_career_pathways
  - courses: 83 GMIoT courses. Key fields: course_id, course_title, provider_id,
    qual_type, level (RQF 1–7), ssa_code, ssa_label, overview, what_you_will_learn,
    entry_requirements, progression, course_url, mode
  - providers: 6 partner institutions (Wigan & Leigh College, University of Salford,
    Trafford & Stockport College, Tameside College, Bury College, Ada College)
  - campuses: physical delivery locations, linked to providers
  - course_career_pathways: career pathway metadata for courses

job_roles_asset.db
  Tables: jobs, job_progression_cache
  - jobs: 1,252 NCS/Prospects job records. Key fields: id, title, source (NCS|Prospects),
    url, level (RQF 1–7), overview, typical_duties, skills_required, entry_routes,
    salary, progression, salary_min, salary_max
  - 36 records have NULL content fields — handle gracefully, do not filter them out
  - salary_min/salary_max use 0 as a null sentinel (not zero salary)
  - The same job can appear from both NCS and Prospects — intentional, do not deduplicate
  - job_progression_cache: Sonnet-generated inbound/outbound progression narratives,
    keyed by job_id + prompt_version. prompt_version = 4 is current; bump to invalidate.

connections.db
  Table: connections
  - 1,349 pre-computed course→job pairs. Fields: course_id, job_id,
    semantic_score (int %), skills_score (int %), created_at
  - Built by scripts/build_connections.py — not updated at runtime
  - /courses/<id>/careers reads from here first; falls back to live Chroma if no rows

analytics.db  (created at startup if absent — not in git)
  Tables: events, access_codes
  - events: session_id, ts, event (session_start|chat_submit|impression|detail_open|
    progression|rate_limit_hit), entity_type, entity_id, entity_title, meta (JSON)
  - access_codes: code, label, expires_at, created_at, used_count
  NOTE: This DB resets on Railway deploy unless a Volume is attached. See Railway
  section below for details.


CHROMA VECTOR STORE — four collections
---------------------------------------
gmiot_courses           overview chunks: title + overview + what_you_will_learn
                        chunk ID: {course_id}_overview
gmiot_jobs              overview chunks: title + overview + typical_duties
                        chunk ID: {job_id}_overview
gmiot_courses_learning  learning chunks: what_you_will_learn only
                        chunk ID: {course_id}_learning
gmiot_jobs_skills       skills chunks: skills_required only
                        chunk ID: {job_id}_skills_only

Cross-collection search works by lifting a stored embedding from one collection
and querying the other with it. Validated — typical cross-collection scores 80–85%.

IMPORTANT: Stale Chroma HNSW lock files on Windows cause 500 errors ("Nothing found
on disk"). Reboot Windows before debugging code if you see these — do not try to
fix it in code.


EXTERNAL SERVICES
-----------------
Voyage AI (voyage-3.5, 1024 dims)
  - Embeds user queries at runtime before Chroma search
  - input_type="query" at runtime; document chunks were embedded with input_type="document"
  - Client: voyageai.Client() — reads VOYAGE_API_KEY from environment

Anthropic API
  - Claude Haiku (claude-haiku-4-5-20251001): main chat turns
  - Claude Sonnet (claude-sonnet-4-6): welcome interview, advisory cards, progression narratives
  - Calls are made via direct httpx POST to https://api.anthropic.com/v1/messages
  - Key: ANTHROPIC_API_KEY from environment
  - 429 rate-limit responses are detected and logged to events table as rate_limit_hit

WELCOME INTERVIEW FLOW
-----------------------
The app starts with a conversational interview. The user types a message (or the
system sends an opening prompt) and the backend runs a two-turn Sonnet call.

Turn 1 — Sonnet analyses the user's message and the conversation history.
  It calls one of two tools:
    continue_interview — ask a follow-up question (when more signal is needed)
    pivot_to_courses   — enough signal to suggest courses; declares:
                         query: search string for Chroma
                         filter: optional SSA code (int) to narrow to a subject
                         acknowledgement: 1-2 sentence message to show the user

Turn 2 (only on pivot)
  Backend executes the Chroma search using the query and optional filter.
  Returns course + job results to the frontend.

Special behaviours:
  - [FILTER:N] in Sonnet output triggers a hard subject filter on SSA code N
    without semantic search (returns all courses for that SSA code)
  - Safeguarding: if user discloses sensitive content, Sonnet acknowledges briefly
    and redirects to courses — it does not engage as a counsellor
  - Escalation after 4 turns without usable signal: offer to browse everything,
    then offer the GMIoT advisor booking link as a graceful exit


MAIN CHAT FLOW
--------------
POST /chat — two-turn Haiku tool-use pattern.

Turn 1 — Haiku specifies searches, given user message + session history.
  Calls specify_searches tool with:
    query_type: "filter" | "intent" | "refine" | "swerve" | "out_of_scope" | "explain"
    searches: list of {query, type (courses|jobs|both), scope, filters}
    collection_action: "build" | "refine" | "replace" | "none"
    acknowledgement: one-sentence response for the bottom bar

  Short-circuit cases (no retrieval):
    out_of_scope — returns acknowledgement only, candidate set unchanged
    explain      — Haiku answers directly (plain call, no tool use, no retrieval).
                   Returns response_text as a system bubble. Not a qualifying interaction.

  Filters Haiku can specify: ssa_label, qual_type, mode, provider, level.

Retrieval (backend)
  For each specified search: embed query via Voyage AI, query Chroma.
  Structural filters use n_results=200; semantic-only searches use n_results=8.

Turn 2 — Haiku selects best matches.
  Receives candidates as plain text, calls select_results tool to pick the best
  matches and write a one-sentence acknowledgement for the bottom bar.

Response to frontend: {results, acknowledgement, candidate_set, session_id}

Sessions are stored in-memory (_sessions dict), 30-minute TTL. Each session
tracks: qualifying_count, advisory_count, seen_ids, last_context, browsing history.


ADVISORY CARDS
--------------
System-initiated after qualifying chat interactions.
  - First advisory: minimum 4 qualifying interactions
  - Subsequent: minimum 5-interaction spacing

Sonnet generates advisory card content using recent session context. If Sonnet
judges nothing is worth surfacing, it returns advisory_item_type="none" and no
card is shown. Advisory cards have a dashed amber border in the central scroll zone.


JOB PROGRESSION
---------------
GET /jobs/<id>/progression

First call per job:
  1. Fetch top 30 nearest jobs from Chroma (cross-collection lift)
  2. Sonnet generates: 2–3 sentence narrative, inbound roles list, outbound roles list
  3. Result cached in job_progression_cache with prompt_version=4

Subsequent calls: read directly from cache. Bump prompt_version in the query
(currently WHERE prompt_version = 4) to invalidate and regenerate.


ADMIN INTERFACE
---------------
Both admin routes require HTTP Basic Auth. Username is ignored; password must
match ADMIN_PASSWORD env var.

/admin/codes
  - Generate codes: auto-generated format {word}-{digits}, optional label and expiry
  - Lists all codes with usage count, expiry, active/expired status
  - Revoke button deletes a code immediately (with JS confirmation)

/admin/analytics
  - ?days=N param (default 30, or "all" for full history)
  - Total sessions, events, chat submits, 429 rate-limit hits
  - Event type breakdown, top courses/jobs by impressions and detail opens
  - Engagement funnel: session_start → chat_submit → detail_open → progression


ACCESS CODE GATING
------------------
When AUTH_ENABLED=true, all non-admin, non-asset routes redirect to /access.
User submits a code, it is checked against analytics.db access_codes, expiry is
checked, used_count is incremented. Session is marked authenticated on success.

The SEED_ACCESS_CODE env var creates a permanent (no expiry) code at startup —
essential on Railway so a working code always exists after a deploy.


INSTITUTION CONFIGURATION
--------------------------
All institution-specific values are in institution_config.py. To deploy
FutureFinder for a different institution, only this file (and the course
database it points to) needs to change.

institution_config.py contains:
  INSTITUTION_NAME        Short name shown in UI ("GMIoT")
  INSTITUTION_FULL_NAME   Full name used in LLM prompts
  INSTITUTION_REGION      Used in provider list heading
  COURSES_DB              Path to the institution's course SQLite database
  PROVIDERS               Dict of provider name → location/note
  SSA_MAP                 Subject tile label → SSA code (int)
  QUAL_FILTER_MAP         Qual tile label → list of qual_type values in courses table
  SUBJECT_AREAS           List of (ssa_label, description) tuples for LLM prompts

api.py imports all of these at startup. LLM system prompts build their
institution-specific sections from these values at module load time.

DEPLOYMENT (RAILWAY)
---------------------
Dockerfile in project root builds the container:
  - Base image: python:3.11-slim
  - Server: gunicorn -w 1 --threads 4 -b 0.0.0.0:8000 api:app

Single worker, 4 threads is intentional — the in-memory session state (_sessions
dict) is not shared across workers, so multiple workers cause session loss.

Railway environment variables required:
  ANTHROPIC_API_KEY     (required)
  VOYAGE_API_KEY        (required)
  SECRET_KEY            (required — use a random string, not the dev default)
  ADMIN_PASSWORD        (set something that isn't "admin")
  AUTH_ENABLED          "true" to gate with access codes
  SEED_ACCESS_CODE      A known code to bootstrap access after deploy

IMPORTANT — analytics.db persistence:
  analytics.db is created at startup if absent. On Railway the filesystem resets
  on every deploy, so analytics history and access codes are lost unless a Railway
  Volume is attached. Known gap — not yet resolved. Options:
    a) Attach a Railway Volume, mount at /data, change ANALYTICS_DB path in api.py
       to point inside it
    b) Migrate to a Railway-managed Postgres database (larger change, better long-term)

The futurefinder-v3 branch is the current Railway production deployment.
This branch (futurefinder-chat-first) contains the chat-first UI rebuild and
needs its own Railway service if you want to stage it separately.


KNOWN ISSUES AND GOTCHAS
-------------------------
- Chroma lock files: stale HNSW locks on Windows cause "Nothing found on disk"
  500 errors. Reboot Windows — do not try to fix in code.

- salary_min/salary_max use 0 as a null sentinel, not zero salary. The
  salary_string() helper handles this — don't bypass it.

- 36 job records have NULL content fields. These are valid rows — handle
  gracefully, do not filter them out.

- analytics.db resets on Railway deploy (no Volume). Always set SEED_ACCESS_CODE
  in Railway env vars, otherwise you can't log in after a deploy.

- Session state is in-memory. State does not survive a server restart or redeploy.
  A single gunicorn worker prevents cross-worker loss but this is not a persistent
  session store.
